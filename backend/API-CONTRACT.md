# Paid photo API

This is a separate Node server. GitHub Pages publishes only `public/` and cannot run it. `PAID_ENABLED` defaults false. Real payment is unavailable until an operator deploys this backend with durable private storage, explicit frontend origins, valid BSC RPC and configured LibTV generation budget.

The backend also serves `public/`; its `/paid-config.js` response uses `apiBase: '/'` without changing the source shipped to GitHub Pages. Same-origin deployment is recommended. All API responses use `Cache-Control: no-store`. There are no public order listings and no player photos under `public/`.

## Player journey

1. `GET /api/health`: `{ ready, reason?, checking?, refreshing?, chainId: 56, recipient, priceBnb: '0.001', priceWei: '1000000000000000', firstFree: true, trialPolicy: 'wallet_device_ip_limits', provider: 'libtv', turnstile: { required: true, siteKey, orderAction: 'photo_order', trialAction: 'photo_trial', checkAction: 'photo_check' }, trialLimits: { total: 20, daily: 5, ipDaily: 2, deviceLifetime: 1, dayTimezone: 'Asia/Shanghai' } }`. Limits reflect runtime configuration. Only the public sitekey is exposed, never the Turnstile or ledger-hashing secrets. This returns an immediate read-only snapshot while slow CLI/RPC checks run in the background. Startup warms the check without delaying the HTTP listener. Before the first successful check, after invalidation, or beyond the 60-second maximum age, it returns `{ ready: false, checking: true, reason: '正在核验 AI 服务，请稍后重试' }` with the same price/policy fields. Completed results have a 20-second cache; an older successful result may be served with `refreshing: true` during a refresh until its age reaches 60 seconds. Refreshes are deduplicated and serialized. A failed check immediately replaces an old ready result. Submission invalidates readiness before capacity can be consumed, and results from earlier checks cannot restore that invalidated readiness. `firstFree` reflects the configured policy even when `ready: false`. Never open a payment or generation prompt unless ready and a configured widget is available; checking is a temporary fail-closed state, not permission to generate.
2. `GET /api/trial?address=0x…&deviceId=<32-byte-base64url>`: validates and normalizes the wallet, browser claim identifier and visitor IP; returns `{ eligible, available, blockReason, policy: 'wallet_device_ip_limits' }`. `available` describes the global daily/lifetime free pool, while `eligible` additionally checks the wallet, browser and visitor IP. `blockReason` is `null`, `wallet_used`, `device_used`, `ip_daily_limit`, `daily_limit`, `total_limit` or `disabled`. Returns 503 `SERVICE_UNAVAILABLE` if backend/provider/RPC is unready. This preview grants nothing. A stable random browser ID must be retained in local storage; it is a claim-control aid, not proof of a unique person. Clearing storage or changing IP can bypass those identities, so CAPTCHA and a finite shared free pool remain necessary. Wallet ownership is verified through the exact order signature. The server's durable ledgers are authoritative.
3. `POST /api/orders` JSON `{ payerAddress, photoDataUrl, character, scene, options, expectedBillingMode, trialDeviceId, turnstileToken }`: first verifies a fresh Turnstile token with action `photo_order`, returned hostname exactly matching the request Origin hostname, and `cdata` equal to `trialDeviceId`; only then can a new order/photo be persisted. Validates a real JPEG/PNG/WebP (12 MiB maximum, 24 MP input maximum, minimum 64×64, no animation), strips metadata and normalizes it to JPEG. Allowed character: `cz`, `heyi`; scene: `terrace`, `cafe`, `street`; options: `gender` male/female, `body` slim/standard/full, `outfit` black/cream/red. Returns 201 with order, `token`, `signatureMessage`, `protectionVersion: 1` and `trialChallengeRequired`. The random order token is returned once and only its hash is stored. Keep it locally to restore the order. The response includes `billingMode: 'free_trial'|'paid'`, `priceBnb` and `priceWei`; free orders have price strings `'0'` and `paymentStatus: 'not_required'`, while paid orders have `'0.001'`/`'1000000000000000'`. `expectedBillingMode` must match the current quote or 409 `TRIAL_CHANGED` is returned. If an unused wallet is blocked by the free pool/browser/IP, missing or free `expectedBillingMode` is rejected with 409 `TRIAL_LIMIT_REACHED`; only an explicitly reconfirmed `'paid'` choice can request a paid quote. Never silently change a free button into a transfer.
4. `POST /api/orders/:id/authorize` Bearer token JSON `{ signature, trialDeviceId?, turnstileToken? }`: `personal_sign` the exact server message. Message binds service, random nonce, wallet, order, chain, receiver, billing mode, exact order price, photo SHA-256, selection and expiry. Signature is verified by ethers and only the order payer can authorize. This checks readiness again and reserves the available payment/generation slot. Every **not-yet-authorized free order**, including old unsigned quotes, also requires a fresh Turnstile token with action `photo_trial`, the current approved Origin hostname and the same device `cdata`. A new order must use the browser identity bound at creation; an old unbound quote binds it at the first successful grant without rewriting its original signature. Free wallet, hashed device/IP claim and `queued` status are saved atomically before a provider call. Its response has **no payment object**, and processing begins directly. No transfer or gas fee is required for the signature. Paid orders already passed the creation challenge and return `awaiting_payment` with `payment: { chainId, to, valueWei, valueHex, data }`. Repeated authorization of already authorized/queued/completed orders is idempotent and does not require another challenge or consume a new trial.
5. **Paid orders only:** ask the wallet to send a native BNB transaction on chain `0x38`. Use the server's `to`, exact `valueHex` and **unaltered `data`**. New paid orders cost 0.001 BNB; the transaction has the usual network gas fee. The data identifies the order. No token approval or smart contract allowance is requested. The player approves the actual transfer separately in their wallet.
6. **Paid orders only:** `POST /api/orders/:id/payment` Bearer token JSON `{ txHash }`: verifies through the server's configured RPC. Requires chain 56, payer equals signed wallet and tx.from/receipt.from, exact receiver, exact stored order wei, exact order data, successful receipt, transaction newer than authorization and canonical matching block hashes. Credit is granted only after the transaction's block is included in RPC's `finalized` state. Unsupported or failed finality checks fail closed. Returns 202. `paymentStatus: 'pending'` means wait; the backend also rechecks independently after the browser closes. Free trial orders reject this endpoint with 409 `PAYMENT_NOT_REQUIRED`, before checking transaction evidence.
7. `GET /api/orders/:id` Bearer token restores free or paid progress. `completed` includes a relative `resultUrl`. Fetch that URL with the same Bearer token and display the JPEG blob. URLs contain no token.
8. `POST /api/orders/:id/retry` Bearer token JSON `{}` only resumes polling an already submitted provider job or safely locates an existing job. It never buys another generation. `failed` or unresolved `review_required` orders require operator handling using their recorded payment or trial reservation.
9. `POST /api/human-check` JSON `{ trialDeviceId, turnstileToken }` verifies the independent `photo_check` action, device `cdata`, current Origin hostname and token single use, returning only `{ verified: true }`. It does not create orders, grant a trial, run a provider, sign or transfer. It is limited to six requests per visitor IP per minute and is used for non-generating deployment verification. Its response is never a reusable authorization credential; order/claim routes still redeem their own fresh tokens.

POST requests require `Content-Type: application/json` and an Origin exactly listed in `FRONTEND_ORIGINS`. An absent/foreign Origin is rejected. CORS is not authentication; bearer/order signatures and chain proof remain mandatory. Tests and trusted direct clients must set a configured Origin explicitly.

Turnstile is always verified on this backend through `https://challenges.cloudflare.com/turnstile/v0/siteverify`, with a ten-second timeout and fail-closed handling for network/non-JSON/upstream errors. Both `success === true` and exact expected action/approved hostname/device cdata are required. Missing, failed or replayed tokens reject with 403 `CHALLENGE_REQUIRED`, `CHALLENGE_FAILED` or `CHALLENGE_REPLAYED`; missing deployment configuration rejects with 503 `CHALLENGE_UNAVAILABLE`. Tokens are reserved before verification to reject concurrent replay and are single use at Cloudflare across backend restarts. Reset the corresponding widget after every attempt before a retry. A `photo_order` token cannot grant a `photo_trial` or replace a `photo_check` token.

Trial preview, new order creation, signed authorization and queued submission require a fresh completed readiness check, not the health snapshot. A fresh request cannot join a check that started before it was received; requests queued before the next check starts share that next round. Existing rounds and the next round are serialized so parallel requests do not spawn duplicate CLI checks. These operations may take longer than the immediate health response and can fail with 503 `SERVICE_UNAVAILABLE`; a stale successful snapshot never overrides their failure.

## State and failure rules

States: `awaiting_authorization`, `awaiting_payment`, `queued`, `submitting`, `generating`, `completed`, `failed`, `review_required`.

Each transaction hash can fund exactly one order. Reserving the hash and queued generation is one atomically written ledger change. Provider submission intent is persisted before the first quota-consuming call. Unknown submission outcomes are reviewed or located read-only by stable id; they are never automatically submitted again. Restarting a saved provider job resumes only polling/download. A failed provider generation retains its payment proof and does not trigger another charge or generation.

Each wallet's free trial is reserved durably at successful signed authorization, before entering the queue. Additional defaults: one claim per browser identity lifetime, two claims per trusted visitor IP per Shanghai calendar day, five free claims per Shanghai calendar day, and twenty free claims lifetime. Device/IP identifiers are HMAC-SHA256 hashes under a stable private secret, not raw identifiers in the claim ledger. The twenty-claim pool is smaller than the separately approved 100-generation provider cap and cannot consume the entire paid generation pool. Both successful and failed/uncertain free reservations stay counted; historical consumed-wallet entries also count. Duplicate authorization is idempotent; concurrent addresses share the serial generation reservation, and concurrent requests from the same wallet cannot grant another free order. Repeated/expired unsigned uploads grant nothing. A restart, cleared browser storage, mixed address casing, rejected signature, result refresh or recoverable retry cannot reset the server's consumed wallet or lifetime pool. Browser/IP changes are not prevented from representing a different identity; the feature must not be advertised as one free image per unique human. Provider submission failure, ambiguous acceptance or terminal generation failure does **not** automatically release the trial. A free trial consumes the operator's configured generation budget just like paid generation; it is free of BNB charge for the player, not free of provider cost.

Store schema v3 retains `consumedTrials` (lowercase wallet → original order) and adds `trialClaims` (order → hashed identities, reservation time and Shanghai day). V1/v2 migrate atomically without rewriting orders, messages, amounts, transaction history or provider budget. Historical claims use original reservation times when available; unknown old device/IP cannot be reconstructed and is not invented. Existing v1/v2 orders honor the exact price already bound to their original message/payment—including legacy 0.0014 or 0.0001 BNB—and their recipient/expiry. Missing/damaged v2 wallet state or v3 claim state refuses startup instead of resetting entitlements.

New paid quotes expire after five minutes; new free quotes retain the existing thirty-minute default. Old signed deadlines are preserved. One unexpired authorized unpaid order still reserves generation capacity so the last provider slot cannot be oversold; the shorter new paid deadline reduces unpaid blocking. A transaction made before expiry can still be claimed later. A confirmed transaction made after expiry is recorded as paid but marked `review_required`, so the receipt is retained for manual fulfilment/refund. This backend has no recipient private key and cannot automatically refund transfers. Submission/poll logs and credentials are not returned by API.

Unsigned uploads are removed after three minutes during maintenance. Authorized unpaid orders without submitted transaction hashes are retained an extra 24 hours, then removed. Unknown hashes exceeding 24 hours move to review and keep evidence. Completed/failed free and paid orders and transaction/wallet/claim ledgers remain durable until operator-managed retention/archive; do not delete entitlement ledgers. Inputs are capped at 256 MiB in total, pending unsigned orders at 32, total orders at 10,000; new orders fail closed when a limit is reached. Basic limits apply: 240 API requests, six new orders and six human-checks per visitor IP per minute; sixty writes per visitor IP/order per minute. These are process-memory request limits, not a multi-instance edge firewall.

## Runtime

`createPaidServer({ config, chain?, provider?, autoProcess?, turnstileFetch? })` is exported for tests. `turnstileFetch` is a dependency-injected test transport, never a public request flag. It returns `{ server, service, close }`. Production uses `deploy/start-paid.ps1`, `sh deploy/start-paid.sh` or `node --env-file=.env backend/server.mjs` (recommended Node 24). `pnpm run start:paid` only loads environment variables already supplied by the process manager; it does not load `.env` automatically. Ethers and sharp are required; exact dependency versions and `pnpm-lock.yaml` are included.

Environment: existing backend/provider variables plus `TURNSTILE_SECRET`, `TURNSTILE_SITEKEY`, `TURNSTILE_HOSTNAMES=xhuozhong.github.io,xhuozhong.com`, `FREE_TRIAL_HMAC_SECRET` (stable private random value of at least 32 characters), `FREE_TRIAL_TOTAL_LIMIT=20`, `FREE_TRIAL_DAILY_LIMIT=5`, `FREE_TRIAL_IP_DAILY_LIMIT=2`, `PAID_ORDER_TTL_SECONDS=300`. Do not include localhost/127.0.0.1 in production expected hostnames. Set `TRUST_CLOUDFLARE_LOOPBACK_PROXY=true` only when the server binds loopback and Cloudflare Tunnel is the trusted local ingress. In that mode the socket peer must also be loopback and writes/trial preview require a valid single `CF-Connecting-IP`; direct non-loopback peers cannot provide a trusted header. Read-only local health and authenticated receipt checks may use their loopback peer without that header. Otherwise forwarded headers are ignored and the socket peer is used. This trusts the local computer, not arbitrary public callers; secure access to that computer. Never trust X-Forwarded-For or enable local-proxy trust on a public listener.

Use exactly **one backend process and one durable volume**. The file lock rejects concurrent processes using the same data directory; JSON atomic writes/mutexes are not a multi-instance database. Keep storage outside `public/` and out of Git. Backup the full private directory securely, especially `orders.json` with both entitlement ledgers, provider journal and order state. Startup refuses unreadable/damaged state rather than resetting used transaction hashes or free trials.

Run `npm run test:paid` for fake-RPC/real-signature/provider-stub tests; these tests make no transfer and request no LibTV generation.

Primary references: [Cloudflare server-side Turnstile validation](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/), [ethers personal-message signature recovery](https://docs.ethers.org/v6/api/hashing/#verifyMessage), [ethers provider API](https://docs.ethers.org/v6/api/providers/), [BSC finalized block API](https://docs.bnbchain.org/bnb-smart-chain/developers/json_rpc/bsc-api-list/).
