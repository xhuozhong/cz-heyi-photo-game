# Paid photo API

This is a separate Node server. GitHub Pages publishes only `public/` and cannot run it. `PAID_ENABLED` defaults false. Real payment is unavailable until an operator deploys this backend with durable private storage, explicit frontend origins, valid BSC RPC and configured LibTV generation budget.

The backend also serves `public/`; its `/paid-config.js` response uses `apiBase: '/'` without changing the source shipped to GitHub Pages. Same-origin deployment is recommended. All API responses use `Cache-Control: no-store`. There are no public order listings and no player photos under `public/`.

## Player journey

1. `GET /api/health`: `{ ready, reason?, checking?, refreshing?, chainId: 56, recipient, priceBnb: '0.001', priceWei: '1000000000000000', firstFree: true, trialPolicy: 'once_per_wallet', provider: 'libtv' }`. This returns an immediate read-only snapshot while slow CLI/RPC checks run in the background. Startup warms the check without delaying the HTTP listener. Before the first successful check, after invalidation, or beyond the 60-second maximum age, it returns `{ ready: false, checking: true, reason: '正在核验 AI 服务，请稍后重试' }` with the same price/policy fields. Completed results have a 20-second cache; an older successful result may be served with `refreshing: true` during a refresh until its age reaches 60 seconds. Refreshes are deduplicated and serialized. A failed check immediately replaces an old ready result. Submission invalidates readiness before capacity can be consumed, and results from earlier checks cannot restore that invalidated readiness. `firstFree` reflects the configured policy even when `ready: false`. Never open a payment or generation prompt unless ready; checking is a temporary fail-closed state, not permission to generate.
2. `GET /api/trial?address=0x…`: validates and normalizes the address; returns `{ eligible: true|false, policy: 'once_per_wallet' }`. Returns 503 `SERVICE_UNAVAILABLE` if backend/provider/RPC is unready. This is a preview and grants nothing; wallet ownership is verified only through the exact order signature. An unsigned upload does not consume eligibility. The benefit is once per wallet address, not once per person; using another wallet is a separate address. Frontend storage or cookies are never the entitlement ledger.
3. `POST /api/orders` JSON `{ payerAddress, photoDataUrl, character, scene, options, expectedBillingMode? }`: validates a real JPEG/PNG/WebP (12 MiB maximum, 24 MP input maximum, minimum 64×64, no animation), strips metadata and normalizes it to JPEG. Allowed character: `cz`, `heyi`; scene: `terrace`, `cafe`, `street`; options: `gender` male/female, `body` slim/standard/full, `outfit` black/cream/red. Returns 201 with order, `token` and `signatureMessage`. Token is returned once and only its hash is stored. Keep the token locally to restore the order. The response always includes `billingMode: 'free_trial'|'paid'`, `priceBnb` and `priceWei`; a free trial has price strings `'0'` and `paymentStatus: 'not_required'`, and subsequent paid orders have `'0.001'`/`'1000000000000000'`. Optional `expectedBillingMode` must match current eligibility or 409 `TRIAL_CHANGED` is returned before persisting a photo/order. Send this field so another tab consuming the trial cannot silently turn a free action into paid checkout.
4. `POST /api/orders/:id/authorize` Bearer token JSON `{ signature }`: `personal_sign` the exact server message. Message binds service, random nonce, wallet, order, chain, receiver, billing mode, exact order price, photo SHA-256, selection and expiry. Signature is verified by ethers and only the order payer can authorize. This checks readiness again and reserves the available payment/generation slot. For `free_trial`, the lowercased wallet → order reservation and `queued` status are saved atomically before a provider call; the response has **no payment object**, and processing begins directly. No transfer or gas fee is required for this signature. For `paid`, response is `awaiting_payment` with `payment: { chainId, to, valueWei, valueHex, data }`.
5. **Paid orders only:** ask the wallet to send a native BNB transaction on chain `0x38`. Use the server's `to`, exact `valueHex` and **unaltered `data`**. New paid orders cost 0.001 BNB; the transaction has the usual network gas fee. The data identifies the order. No token approval or smart contract allowance is requested. The player approves the actual transfer separately in their wallet.
6. **Paid orders only:** `POST /api/orders/:id/payment` Bearer token JSON `{ txHash }`: verifies through the server's configured RPC. Requires chain 56, payer equals signed wallet and tx.from/receipt.from, exact receiver, exact stored order wei, exact order data, successful receipt, transaction newer than authorization and canonical matching block hashes. Credit is granted only after the transaction's block is included in RPC's `finalized` state. Unsupported or failed finality checks fail closed. Returns 202. `paymentStatus: 'pending'` means wait; the backend also rechecks independently after the browser closes. Free trial orders reject this endpoint with 409 `PAYMENT_NOT_REQUIRED`, before checking transaction evidence.
7. `GET /api/orders/:id` Bearer token restores free or paid progress. `completed` includes a relative `resultUrl`. Fetch that URL with the same Bearer token and display the JPEG blob. URLs contain no token.
8. `POST /api/orders/:id/retry` Bearer token JSON `{}` only resumes polling an already submitted provider job or safely locates an existing job. It never buys another generation. `failed` or unresolved `review_required` orders require operator handling using their recorded payment or trial reservation.

POST requests require `Content-Type: application/json` and an Origin exactly listed in `FRONTEND_ORIGINS`. An absent/foreign Origin is rejected. CORS is not authentication; bearer/order signatures and chain proof remain mandatory. Tests and trusted direct clients must set a configured Origin explicitly.

Trial preview, new order creation, signed authorization and queued submission require a fresh completed readiness check, not the health snapshot. A fresh request cannot join a check that started before it was received; requests queued before the next check starts share that next round. Existing rounds and the next round are serialized so parallel requests do not spawn duplicate CLI checks. These operations may take longer than the immediate health response and can fail with 503 `SERVICE_UNAVAILABLE`; a stale successful snapshot never overrides their failure.

## State and failure rules

States: `awaiting_authorization`, `awaiting_payment`, `queued`, `submitting`, `generating`, `completed`, `failed`, `review_required`.

Each transaction hash can fund exactly one order. Reserving the hash and queued generation is one atomically written ledger change. Provider submission intent is persisted before the first quota-consuming call. Unknown submission outcomes are reviewed or located read-only by stable id; they are never automatically submitted again. Restarting a saved provider job resumes only polling/download. A failed provider generation retains its payment proof and does not trigger another charge or generation.

Each wallet's free trial is reserved durably at successful signed authorization, before entering the queue. Duplicate authorization is idempotent; concurrent addresses share the serial generation reservation, and concurrent requests from the same wallet cannot grant another free order. Repeated/expired unsigned uploads grant nothing. A restart, cleared browser storage, mixed address casing, rejected signature, result refresh or recoverable retry cannot reset the consumed trial. Provider submission failure, ambiguous acceptance or terminal generation failure does **not** automatically release the trial: retain and recover the original order or handle it manually. A free trial consumes the operator's configured LibTV generation budget exactly like a paid generation; it is free of BNB charge for the player, not free of provider cost.

Store schema v2 adds `consumedTrials` (lowercase wallet address → original order id). V1 migrates atomically without rewriting existing messages, amounts or transaction history. Existing v1 and v2 orders honor the exact price already bound to their original message/payment—including legacy 0.0014 or 0.0001 BNB; only newly created paid orders use 0.001 BNB. Restarting does not rewrite old signatures or payment amounts, and existing trial reservations remain consumed. Missing/damaged v2 trial state or a signed free order lacking its reservation refuses startup instead of resetting entitlements.

Authorization expires after 30 minutes by default. A transaction made before expiry can still be claimed later. A confirmed transaction made after expiry is recorded as paid but marked `review_required`, so the receipt is retained for manual fulfilment/refund. This backend has no recipient private key and cannot automatically refund transfers. Submission/poll logs and credentials are not returned by API.

Unsigned uploads are removed after three minutes during maintenance. Authorized unpaid orders without submitted transaction hashes are retained an extra 24 hours, then removed. Unknown hashes exceeding 24 hours move to review and keep evidence. Completed/failed free and paid orders and both transaction/trial ledgers remain durable until operator-managed retention/archive; do not delete either entitlement ledger. Inputs are capped at 256 MiB in total, pending unsigned orders at 32, total orders at 10,000; new orders fail closed when a limit is reached. Basic IP limits apply without trusting client-provided forwarding headers.

## Runtime

`createPaidServer({ config, chain?, provider?, autoProcess? })` is exported for tests. It returns `{ server, service, close }`. Production uses `deploy/start-paid.ps1`, `sh deploy/start-paid.sh` or `node --env-file=.env backend/server.mjs` (recommended Node 24). `pnpm run start:paid` only loads environment variables already supplied by the process manager; it does not load `.env` automatically. Ethers and sharp are required; exact dependency versions and `pnpm-lock.yaml` are included.

Environment: `PAID_ENABLED=true`, `AI_FIRST_FREE=true` (default; set `false` to disable new trial grants), `BSC_RPC_URL=https://…`, `PAID_DATA_DIR=/private/persistent/path`, `FRONTEND_ORIGINS=https://paid.example`, `HOST=127.0.0.1`, `PORT=4176`, `SERVICE_DOMAIN=paid.example`, plus LibTV configuration in the provider/deployment guide. Bind behind an HTTPS reverse proxy. Forwarding headers are intentionally not trusted, so a single reverse proxy shares the server IP rate limit unless a production rate limiter is added at that proxy.

Use exactly **one backend process and one durable volume**. The file lock rejects concurrent processes using the same data directory; JSON atomic writes/mutexes are not a multi-instance database. Keep storage outside `public/` and out of Git. Backup the full private directory securely, especially `orders.json` with both entitlement ledgers, provider journal and order state. Startup refuses unreadable/damaged state rather than resetting used transaction hashes or free trials.

Run `npm run test:paid` for fake-RPC/real-signature/provider-stub tests; these tests make no transfer and request no LibTV generation.

Primary references: [ethers personal-message signature recovery](https://docs.ethers.org/v6/api/hashing/#verifyMessage), [ethers provider API](https://docs.ethers.org/v6/api/providers/), [BSC finalized block API](https://docs.bnbchain.org/bnb-smart-chain/developers/json_rpc/bsc-api-list/).
